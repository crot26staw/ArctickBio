# АрктикБио — перенос вёрстки на WordPress

Как натягиваем готовую статическую вёрстку (`src/`, см. `CLAUDE.md`) на **WordPress + WooCommerce**. Этот файл — правила и план для Claude Code на этапе интеграции. Общение с пользователем — на русском.

## Стек
| Что | Чем |
|---|---|
| Товары, корзина, заказы, личный кабинет | **WooCommerce** (классический checkout на шорткоде, не Checkout Block) |
| Поля страниц, настройки темы, поля товаров/записей | **Carbon Fields** (Composer-пакет `htmlburger/carbon-fields` внутри темы) |
| Отправка почты (письма WP и WooCommerce, наши формы) | **WP Mail SMTP** — мы только вызываем `wp_mail()`, SMTP настраивается в плагине |
| Свои формы (вход, регистрация, сброс пароля, ЛК и т.п.) | Свои AJAX-обработчики (`admin-ajax.php` / REST + nonce), без Contact Form 7 |
| CSS / JS | Тот же Vite-проект: сборка в тему, подключение по `manifest.json` |

Другие плагины не ставить без согласования с пользователем.

## Где лежит тема
Папка `wp-theme/arctik-bio/` в этом репозитории. **Вся работа по WordPress коммитится и пушится в ветку `wordpress`** (`main` — статика для GitHub Pages). Ядро WP, плагины, загрузки и база в git не попадают.

## Локальное окружение (Docker)
- `docker-compose.yml` в корне репо (проект `arctik-bio`): `wordpress` (php8.2-apache — как на хостинге), `db` (MariaDB 11.4), `mailpit` (ловушка писем), `phpmyadmin`, `wpcli` (профиль `cli`, только по `run`). Данные — тома `wp_data`, `db_data`.
- Адреса (порты 8080/8025 заняты другими проектами пользователя): сайт — `http://localhost:8095` (админка `admin` / `admin`), письма — `http://localhost:8096`, phpMyAdmin — `http://localhost:8097`.
- Тема монтируется в контейнер: `./wp-theme/arctik-bio` → `wp-content/themes/arctik-bio`. Лимиты PHP (загрузка 64M под видео) — `docker/php.ini`.
- Настройки — `.env` (в `.gitignore`), шаблон — `.env.example`.
- **Первый запуск / восстановление:** `./scripts/wp-setup.sh` — поднимает контейнеры, ставит WP, русский язык, WooCommerce и WP Mail SMTP (+ переводы), постоянные ссылки `/%postname%/`, рубли и Россию, страницы WC с русскими названиями (каталог — `/catalog/`), WP Mail SMTP → Mailpit. Повторный запуск безопасен.
- **WP-CLI:** `docker compose run --rm wpcli wp <команда>` (слово `wp` обязательно — без него образ не запускает WP-CLI). Остановить окружение — `docker compose stop`, удалить вместе с базой — `docker compose down -v`.
- Composer запускается на хосте (установлен через brew): `composer install -d wp-theme/arctik-bio`.

## Деплой (Reg.ru)
Хостинг Reg.ru (ISPmanager), **SSH нет — всё по FTP** (+ phpMyAdmin из панели для базы). На хостинге в панели выставить PHP 8.2+. Деплой статики на GitHub Pages (`deploy.yml`) остаётся как есть — для показа вёрстки.

### Тема — GitHub Actions по FTP
- Workflow `deploy-theme.yml`, запуск вручную (`workflow_dispatch`) и по тегу `theme-v*`: `npm ci` → `npm run build:wp` → `composer install --no-dev --optimize-autoloader` в теме → выгрузка папки темы по FTP в `www/<домен>/wp-content/themes/arctik-bio/` (`SamKirkland/FTP-Deploy-Action` — грузит только изменённые файлы, ведёт `.ftp-deploy-sync-state.json` на сервере).
- Не выгружаются: `node_modules`, исходники, `.env`, `composer.lock` — список исключений в workflow.
- Доступы — GitHub Secrets: `FTP_HOST`, `FTP_USER`, `FTP_PASSWORD`, `FTP_THEME_PATH`. FTPS, если Reg.ru его даёт.
- WordPress и плагины на хостинге ставятся один раз (установщик Reg.ru или вручную по FTP), версии — как локально.

### База и загрузки — перенос локальной БД на хостинг
Контент наполняется **локально**, затем база и `uploads` переносятся на хостинг. Скрипт `scripts/db-export.sh` (через WP-CLI в Docker):
1. `wp search-replace 'http://localhost:8095' 'https://<домен>' --all-tables --export=dump.sql` — дамп с заменой адресов (WP-CLI корректно правит сериализованные данные; локальная база не меняется). Префикс таблиц локально и на хостинге — одинаковый.
2. Дамп импортируется в phpMyAdmin на Reg.ru (большой — сжать в `.sql.gz`; если упрётся в лимит загрузки — бить на части).
3. `wp-content/uploads` выгружается по FTP (`lftp mirror -R` или вручную).
4. На хостинге: пересохранить постоянные ссылки, проверить настройки WP Mail SMTP (SMTP-доступы на проде свои), сбросить кеш.

**Важно:** перенос базы целиком — только **до запуска магазина** (пока на проде нет заказов и клиентов). После запуска база на хостинге главная: заказы и пользователи живут там, локальную базу поверх неё не заливать — правки контента делаются в админке на проде (или переносятся точечно, согласовать).

## Сборка ассетов (Vite → тема)
- Исходники SCSS/JS остаются в `src/` — **единый источник** стилей и скриптов для статики и темы. Дублировать стили в теме нельзя.
- Отдельный режим сборки `npm run build:wp` (`vite build --mode wp`): вход — `src/js/main.js` + `src/scss/main.scss`, выход — `wp-theme/arctik-bio/dist/` с `manifest.json`. Обычный `npm run build` (статика, GitHub Pages) не трогаем.
- `inc/vite.php`: в продакшене читает манифест и делает `wp_enqueue_style` / `wp_enqueue_script` (`type="module"`) с хешированными файлами; если запущен dev-сервер (`npm run dev:wp`, проверка — файл `dist/hot` или константа в `wp-config.php`) — подключает `@vite/client` и исходники с dev-сервера.
- Картинки/шрифты, на которые ссылается SCSS, обрабатывает Vite (попадают в `dist/`). Картинки, иконки и видео, которые выводит PHP-разметка, копируются в `wp-theme/arctik-bio/assets/` без хешей и выводятся через `arctik_asset('images/…')`. Контентные картинки (товары, сотрудники, новости, фото секций) — из медиатеки через поля.
- Стили WooCommerce по умолчанию отключаем (`woocommerce_enqueue_styles` → `[]`), стили блоков Gutenberg на фронте тоже — вёрстка своя.

## Как переносить разметку
1. **Разметку не переписываем, а переносим**: HTML из `src/` и `partials/` копируется в PHP как есть — те же классы БЭМ, те же `data-js-*`, та же структура. Любое отличие разметки = риск сломать стили/JS. Если без изменения разметки никак (например, WooCommerce требует свою обёртку) — сказать пользователю и поправить и статику, и SCSS.
2. Partial → `template-parts/…php`, подключение — `get_template_part( 'template-parts/home/hero', null, $args )`. Переменные `{{ title }}` из `data` → `$args['title']`.
3. Весь вывод экранируется: `esc_html()`, `esc_attr()`, `esc_url()`, для текста с разметкой из полей — `wp_kses_post()`.
   **Типограф**: неразрывные пробелы в текстах из админки расставляются автоматически на выводе — функция `arctik_typograph()` в `inc/typograph.php` по тем же правилам, что в `CLAUDE.md` (после слов из 1–2 букв и без/для/при/про/под/над/или/что/как; перед ли/же/бы и перед «—»; между числом и словом/единицей, разряды чисел). Не трогает содержимое тегов и атрибутов. Подключена к `the_title`, `the_content`, `the_excerpt`, `woocommerce_short_description`; тексты из Carbon Fields выводятся через `arctik_text()` / `arctik_field()`, которые её вызывают. Вручную `&nbsp;` в поля не вписывать. В атрибуты (`alt`, `aria-label`, `value`) — без типографа.
4. Картинки — через хелпер, который выдаёт `<img>` из вложения с `width`/`height`, `alt` из медиатеки, `loading="lazy"` (кроме первого экрана) и `srcset`. Формат — webp, как в статике.
5. Меню — `wp_nav_menu()` с разметкой `ul.menu > li.menu-item > a`, классы под нашу вёрстку через `menu_class` / фильтры `nav_menu_css_class`, `nav_menu_link_attributes` (сюда же — `data-js-roll` и т.п.).
6. Пути в разметке: никаких `./assets/...` — только `arctik_asset()`, `get_permalink()`, `wc_get_page_permalink()` и т.д. Ссылки между страницами — из WP, не хардкод.
7. Демо-логика в JS (`onSubmit`-заглушки в auth.js, демо-пересчёт в cart.js, «Промокод не найден» в promo.js, демо-переход в checkout.js, демо-списки в pickup.js / address.js) заменяется на реальные запросы. Сами модули и разметку состояний не меняем — меняем только источник данных. Данные для JS (ajax URL, nonce, тексты) — `wp_localize_script` / `wp_add_inline_script` в объект `window.arctik`.
8. Тексты-заглушки из вёрстки (повторённые ответы FAQ, одинаковые товары, `#`-ссылки) в шаблон не хардкодим — они становятся контентом в полях/записях; в базу при первом наполнении можно занести текущие тексты из вёрстки.

## Контент: поля или тип записи — СПРАШИВАТЬ
Когда в секции есть повторяющиеся элементы или контент, которым, похоже, будут управлять отдельно (сотрудники, новости, отзывы, FAQ, шаги «Процесса», исследования/документы, города и магазины, соцсети и т.п.), **не решать самому**. Остановиться и спросить пользователя:

> «Блок «…»: делаем отдельный тип записи (`arctik_xxx`) или поля Carbon Fields (complex-поле на странице / в настройках темы)?»

В вопросе коротко дать аргументы: где элемент используется (одна страница или несколько), нужна ли у элемента своя страница/URL, сколько их будет, нужна ли сортировка/фильтрация. Решение записать в таблицу ниже.

Без вопроса:
- Товары, заказы, клиенты, корзина — всегда WooCommerce. Товар — **вариативный**: вкус и формат (15 / 30 саше, «Набор на 3 месяца») — глобальные атрибуты (`pa_…`) и вариации; выбор формата (`product-format.js`) работает по вариациям (цена, наличие, `variation_id` в форме).
- Обычные тексты и картинки конкретной секции конкретной страницы — поля Carbon Fields этой страницы.
- Общее для всего сайта (телефон, почта, адрес, соцсети в футере, ссылки на документы) — **Theme Options** Carbon Fields (`arctik_option( 'phone' )`).

## Carbon Fields — соглашения
- Префикс всех полей и опций — `arctik_`. Имена — snake_case по смыслу (`arctik_hero_title`, `arctik_team` complex).
- Контейнер полей — по шаблону страницы (`where( 'post_template', '=', 'page-templates/about.php' )`, для главной — `where( 'post_id', '=', get_option( 'page_on_front' ) )`).
- **Каждый блок страницы — отдельная вкладка** (`add_tab( 'Первый экран', [...] )`, `add_tab( 'О бренде', [...] )`…): одна секция вёрстки = одна вкладка, вкладки в порядке секций на странице, названия — по-русски, как секции называются для пользователя. Поля одной секции не разносить по вкладкам и не смешивать в одной вкладке поля разных секций. То же для товара и Theme Options (вкладки «Контакты», «Соцсети», «Документы», «Подвал»…). Секции, взятые с главной на другие страницы (video, usage, benefits, comparison, «Процесс»), — спросить: общие поля в Theme Options или своя вкладка на каждой странице.
- Подписи полей — по-русски, понятные контент-менеджеру; где нужно — `set_help_text` (размер картинки, лимит текста).
- Повторяющиеся элементы внутри страницы — `complex` с `set_header_template` (чтобы в админке было видно, что за элемент).
- Получение значений — только в шаблоне секции или в хелпере, не в `functions.php`.
- У каждого поля, которое выводится, должно быть разумное поведение, когда оно пустое (секция/элемент не выводится, а не ломается вёрстка).

## WooCommerce — соглашения
- Тема объявляет `add_theme_support( 'woocommerce' )`, шаблоны переопределяются в `woocommerce/` только когда без этого никак; в остальном — хуки (`remove_action` / `add_action`) в `inc/woocommerce.php`.
- Карточки в цикле: `ul.products > li.product`, `.woocommerce-loop-product__title`, `.price`, `.button.add_to_cart_button.ajax_add_to_cart` с `data-product_id` (как в вёрстке).
- Корзина-попап (`.mini-cart`) — обновляется фрагментами WC (`woocommerce_add_to_cart_fragments`), счётчик в шапке — тоже фрагмент. Изменение количества / удаление — AJAX.
- Checkout — `[woocommerce_checkout]` с нашим `checkout/form-checkout.php`; поля — через `woocommerce_checkout_fields` под нашу разметку. Способы доставки/оплаты, ПВЗ, карта — отдельный этап (см. «Открытые вопросы»).
- Личный кабинет — эндпоинты `my-account` (`orders`, `edit-account`, `edit-address`, `view-order`), шаблоны в `woocommerce/myaccount/` под нашу вёрстку.
- Вход / регистрация / сброс пароля из попапа — свои AJAX-обработчики на `wp_signon()`, `wc_create_new_customer()`, `retrieve_password()` / `reset_password()`; ошибки возвращаются в формате, который понимает `field.js` (`setFieldError`). Ссылка из письма сброса ведёт на `#auth-reset` (экран попапа).
- Все письма уходят через WP Mail SMTP; шаблоны писем WC — отдельной задачей, если пользователь попросит.

## AJAX и безопасность
- Каждый обработчик: проверка nonce (`check_ajax_referer`), санитизация (`sanitize_text_field`, `sanitize_email`, `absint`…), проверка прав (`is_user_logged_in`, `current_user_can`), ответ — `wp_send_json_success` / `wp_send_json_error` с полем `errors: { fieldName: 'текст' }` для подсветки полей.
- Тексты ошибок — по-русски, те же, что в вёрстке (с ` ` / `&nbsp;` по правилам из `CLAUDE.md`).

## Сессии и контекст
- **Старт сессии:** прочитать `CLAUDE.md`, этот файл (обязательно «Текущее состояние» и «Принятые решения»), `git status` / `git log -5`. Продолжать с «Следующего шага». Не перечитывать весь проект — только файлы текущего этапа (статика страницы, её partials, нужные JS-модули, уже сделанные PHP-шаблоны, на которые этап опирается).
- **Экономить контекст:** большие файлы читать частями (`offset`/`limit`, `grep`), не выводить целиком сборку и логи, Figma на этом этапе не нужна — эталон — статика (`npm run dev`); скриншоты — только для сверки секции, не на каждый шаг.
- **Признаки, что контекст заканчивается:** в разговоре появилось автоматическое сжатие (сводка предыдущей части разговора), этап занял много шагов, прочитано много больших файлов, начинаешь терять детали ранее принятых решений.
- **Что делать при таком признаке** (и всегда в конце этапа):
  1. Довести текущий шаг до рабочего состояния — не оставлять сломанный шаблон или полуперенесённую секцию.
  2. Обновить «Текущее состояние», таблицу этапов и «Принятые решения».
  3. Предложить пользователю закоммитить и запушить в ветку `wordpress` (только с его согласия).
  4. Сказать пользователю прямо: «Контекст заполнен, дальше лучше в новой сессии. Начните её фразой: *Продолжаем интеграцию WordPress по WORDPRESS.md*».
- Не начинать следующий этап в той же сессии, если текущий был большим, — сначала предложить новую сессию.

## Порядок работы над страницей
1. Перечитать статическую страницу и её partials, составить список секций и контента.
2. Задать пользователю вопросы «тип записи или поля» (см. выше) и про всё неясное — до начала кода.
3. Сделать шаблон, секции в `template-parts/`, поля Carbon Fields (вкладка на блок), заполнить контент текстами/картинками из вёрстки.
4. Сверить в браузере с локальной статикой (`npm run dev`) на 1440, 768, 375: разметка и вид должны совпадать, JS — без ошибок в консоли.
5. Обновить таблицу этапов, «Принятые решения» и «Текущее состояние».
6. Не переходить к следующей странице без подтверждения пользователя.

**Статика и PHP — в синхроне.** Любая правка разметки после переноса страницы делается в двух местах: в `src/` (страница/partial) и в PHP-шаблоне, в одном коммите. Стили и JS — только в `src/`, они общие. Статика должна оставаться рабочей.
